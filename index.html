Cloud Cost Optimizer

backend · async

You register a cloud server with the service and it comes back with recommendations for cutting its cost. The analysis is slow, so the API never does it on the request thread: it writes the job down and a background worker picks it up.

  • FastAPI
  • PostgreSQL
  • Celery
  • Redis
  • Azure
  • LLM API
  • Docker

How a request moves through it

  1. 01A FastAPI endpoint takes the server registration, validates it, and saves it to PostgreSQL.
  2. 02Instead of analysing right there, it puts a task on Redis and returns immediately, so the caller is not left waiting.
  3. 03A Celery worker pulls the task off the queue and gathers the server's usage and configuration details.
  4. 04An LLM API call turns those raw numbers into recommendations written in plain language.
  5. 05The worker writes the recommendations back to PostgreSQL, where the API can read them on the next request.

Why it is built this wayCost analysis takes long enough that doing it inside the HTTP request would time out or block a worker process. Splitting it into an API tier and a worker tier means the two scale separately, and a failed analysis can be retried without the user resubmitting anything. The whole stack runs in Docker so the API, the workers, Redis and Postgres come up together.
