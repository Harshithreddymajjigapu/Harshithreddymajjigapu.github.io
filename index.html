Cloud Cost Optimizer

backend · async

You register a cloud server with the service and it comes back with recommendations for cutting its cost. The analysis is slow, so the API never does it on the request thread: it writes the job down and a background worker picks it up.

  • FastAPI
  • PostgreSQL
  • Celery
  • Redis
  • Azure
  • LLM API
  • Docker

How a request moves through it

  1. 01A FastAPI endpoint takes the server registration, validates it, and saves it to PostgreSQL.
  2. 02Instead of analysing right there, it puts a task on Redis and returns immediately, so the caller is not left waiting.
  3. 03A Celery worker pulls the task off the queue and gathers the server's usage and configuration details.
  4. 04An LLM API call turns those raw numbers into recommendations written in plain language.
  5. 05The worker writes the recommendations back to PostgreSQL, where the API can read them on the next request.

Why it is built this wayCost analysis takes long enough that doing it inside the HTTP request would time out or block a worker process. Splitting it into an API tier and a worker tier means the two scale separately, and a failed analysis can be retried without the user resubmitting anything. The whole stack runs in Docker so the API, the workers, Redis and Postgres come up together.

Real-Time Transaction Streaming

streaming · event-driven

A Kafka pipeline that takes a live stream of card transactions and does two independent things with every single one: keeps a permanent record of it, and scores it for risk. Neither job can hold the other up, and neither can lose a message because the other was down.

  • Python
  • Apache Kafka
  • MongoDB
  • TensorFlow / Keras
  • scikit-learn
  • Docker

How a transaction moves through it

  1. 01A producer stands in for a card terminal, publishing one transaction per second onto the Kafka topic transactions.
  2. 02Two separate consumer groups subscribe to that same topic. Because they are separate groups, each one receives every message rather than splitting them.
  3. 03The first group writes the transaction straight to MongoDB as the permanent record, indexed on id and timestamp.
  4. 04The second group scales the amount and runs it through a small Keras model, then writes a risk score, a verdict and the model version to a second collection.
  5. 05The whole stack — Kafka in KRaft mode, no ZooKeeper, plus MongoDB with a persistent volume — comes up from one Docker Compose file.

Why it is built this wayTwo consumer groups instead of one consumer doing both jobs. Each group tracks its own position in the stream, so the scoring side can be restarted, swapped for a better model, or fall behind under load without the record of what was actually transacted ever missing a row. The scoring model itself is trained on synthetic data and is a placeholder for a real one — the point of the project is the pipeline around it.
